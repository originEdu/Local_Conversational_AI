Local Conversational AI — 동작 원리

메타휴먼과 한국어로 대화하는 프로그램. 사용자가 텍스트를 입력하면 로컬 LLM이 답하고, 로컬 TTS가 음성을 만들고, 메타휴먼이 그 음성에 맞춰 입을 움직인다. 외부 API를 쓰지 않는다. 전부 한 대의 PC에서 돈다.

프로세스는 두 개다.

ollama serve          # 설치만 하면 됨. 작성한 코드 없음
uvicorn app.main:app  # 이 프로젝트의 서버 코드 전부

UE는 서버 하나만 안다. Ollama도 TTS도 UE에 노출되지 않는다.

2한 번의 대화가 흐르는 순서

사용자가 "오늘 뭐 했어?"라고 입력했을 때 벌어지는 일이다.

  1. 질문이 서버로

    {"type": "user_message", "text": "오늘 뭐 했어?"}

  2. 히스토리에 쌓고 LLM 호출

    이 연결의 대화 기록에 질문을 붙이고, system 프롬프트와 함께 Ollama에 스트리밍 요청을 보낸다.

    [
  {"role": "system", "content": "너는 사용자와 편하게 대화하는 친구다..."},
  {"role": "user",   "content": "오늘 뭐 했어?"}
]

  3. 토큰을 모으다 문장이 완성되면 자른다

    LLM은 글자를 조금씩 흘려보낸다. 버퍼에 모으다가 문장이 끝나면 그 문장만 떼어낸다.

    "음," → "음, 그냥" → "음, 그냥 책 읽으면서" → "음, 그냥 책 읽으면서 커피 마셨어!"
                                                                        ↑ 확정

    이게 체감 속도의 핵심이다. 전체 답변을 다 기다리면 5~8초 침묵이 생긴다. 첫 문장만 나오면 바로 말을 시작하므로 2초 안에 입이 움직인다.

    자르는 규칙은 네 가지다.

    • 경계 문자는 . ? ! … 줄바꿈
    • 10자 미만이면 다음 경계까지 합친다. "응."을 따로 합성하면 오디오가 뚝 끊긴다
    • 120자를 넘으면 강제로 자른다. LLM이 마침표를 안 찍는 경우 대비
    • 읽을 내용이 없으면 버린다. LLM이 이모지만 따로 뱉는 일이 잦은데, 그대로 합성하면 입은 가만있고 소리만 1초 난다

  4. 문장을 음성으로

    "음, 그냥 책 읽으면서 커피 마셨어!"  →  44100Hz 파형 3916ms

  5. 음성과 글자를 시간 축에서 맞춘다 (강제 정렬)

    만들어진 음성과 원래 문장을 wav2vec2 CTC 모델에 같이 넣으면, 각 음절이 몇 밀리초에 발음되는지 나온다.

    안      0 ~   340ms
녕    340 ~   440ms
하    440 ~   681ms
세    681 ~   801ms
요    801 ~  1883ms

    이 단계가 없으면 입 모양을 언제 바꿔야 할지 알 수 없다.

  6. 음절을 입 모양으로

    한국어 입 모양은 중성(모음)이 지배한다. 밤을 발음할 때 입을 크게 벌리는 건 ㅏ 때문이지 ㅂ이나 ㅁ 때문이 아니다.

    그래서 음절마다 중성으로 기본 입 모양을 정하고, 초성·종성은 앞뒤 일부만 덮어쓴다.

    "밤" (ㅂ + ㅏ + ㅁ), 구간 0~200ms

  PP   0 ~  50ms   앞 25%  — 초성 ㅂ, 입을 다물었다 연다
  AA  50 ~ 160ms   가운데  — 중성 ㅏ, 턱을 벌린다
  PP 160 ~ 200ms   뒤 20%  — 종성 ㅁ, 다시 다문다
    viseme언제입 모양
    AAㅏ ㅑ ㅐ ㅘ턱을 크게 벌림
    EHㅓ ㅕ ㅔ ㅝ중간으로 벌림
    IHㅣ옆으로 당김
    OHㅗ ㅛ둥글게
    OUㅜ ㅠ ㅚ ㅟ오므림
    EUㅡ ㅢ옆으로 폄
    PPㅁ ㅂ ㅍ완전히 다뭄
    NNㄴ ㄷ ㅌ ㄹ살짝 벌림
    KKㄱ ㅋ살짝 벌림
    SSㅅ ㅈ ㅊ좁게
    sil무음닫음

  7. 프레임 하나로 묶어 전송

    텍스트·오디오·입 모양을 한 덩어리로 보낸다.

    {
  "type": "speech",
  "seq": 0,
  "text": "음, 그냥 책 읽으면서 커피 마셨어!",
  "audioBase64": "UklGRi...",
  "visemes": [
    {"v": "EU", "start": 0,   "end": 340},
    {"v": "NN", "start": 340, "end": 440}
  ]
}

    3~7단계가 문장마다 반복된다. 답변이 끝나면 마지막에 알린다.

    {"type": "turn_end", "seq": 2}

  8. UE가 재생

    프레임을 큐에 쌓고, 앞 문장 재생이 끝나면 다음 문장을 시작한다. 재생 시각에 해당하는 viseme을 찾아 메타휴먼 얼굴 커브에 값을 넣는다.

    값을 그대로 넣으면 입이 딱딱 끊기므로 FInterpTo로 부드럽게 잇는다.

3왜 이렇게 만들었나

왜 파이썬 한 프로세스인가

TTS(MeloTTS, XTTS)와 정렬기(wav2vec2)는 파이썬 라이브러리다. 자바에서 부를 방법이 사실상 없다. 그래서 파이썬 프로세스는 어차피 떠야 한다.

처음에는 Spring Boot를 앞에 두는 안을 검토했다. 그러면 프로세스가 하나 늘고 서비스 간 HTTP 홉이 생긴다. 취미 프로젝트에서 그 비용을 치를 이유가 없어 FastAPI 단일로 정했다.

계층은 문서상 나눠두되 물리적으로는 한 프로세스다. 파이썬끼리 HTTP를 태울 이유가 없다.

왜 WebSocket인가

문장이 완성될 때마다 서버가 먼저 밀어야 한다. REST면 클라이언트가 계속 물어봐야 하고, 그러면 문장 단위 스트리밍의 이점이 사라진다.

왜 음절 단위인가

음소 단위로 하면 매핑 표가 커지고 정렬도 어려워진다. 한국어는 입 모양이 모음에 지배되므로 음절 단위로도 화면에서 차이가 거의 없다.

왜 정렬기를 CPU에 두나

GPU 8GB를 LLM(1.6GB)과 TTS(0.9GB)가 쓴다. 정렬기는 문장당 100~200ms면 충분해서 GPU에 올릴 이유가 없다.

4고장 나도 대화는 계속된다

텍스트가 최소 보장선이다. 무슨 일이 생겨도 자막은 나간다.

고장결과
Ollama가 죽음{"type":"error","code":"LLM_UNAVAILABLE"}. 서버는 안 죽는다
TTS 실패audioBase64: null, visemes: []. 자막만 나가고 입은 가만있다
정렬 실패오디오 길이를 음절 수로 균등 분배. 정확도는 떨어지지만 멈추지 않는다
연결 끊김UE가 3회 재연결. 대화 기록은 초기화된다 (연결 = 세션)
히스토리 초과오래된 대화부터 버린다. system 프롬프트는 항상 유지

5코드 구조

server/app/
  main.py       FastAPI 앱, WebSocket 엔드포인트, 모델 사전 로딩
  session.py    대화 히스토리, 턴 오케스트레이션
  llm.py        Ollama 스트리밍 호출
  sentence.py   토큰 스트림을 문장으로 분할
  pipeline.py   speech 프레임 조립, 실패 폴백
  tts.py        TTS 프로토콜, MeloTTS·XTTS 구현체, WAV 인코딩
  align.py      균등 분배 폴백, wav2vec2 CTC 정렬
  viseme.py     음절 → viseme 매핑
  hangul.py     한글 자모 분해
  config.py     환경변수 설정

의존 방향은 한 방향이다.

main → session → pipeline → tts, align, viseme → hangul

hangul, viseme, sentence는 아무것도 import하지 않는 순수 함수 모듈이다. 그래서 모델도 GPU도 없이 테스트할 수 있다. 전체 단위 테스트 56개가 1초 안에 끝난다.

6TTS 엔진 두 가지

TTS_ENGINE 환경변수로 고른다. 기본은 melo.

MeloTTSXTTS-v2
한글 처리직접로마자로 바꾼 뒤 다국어 모델이 읽음
발음자연스러움외국인 억양
음성 복제불가가능 (참조 음성 6초)
같은 문장 길이4357ms8534ms
VRAM902MB1899MB
라이선스MITCPML (비상업 전용)

XTTS는 음성 복제가 되지만 한국어를 로마자로 바꿔 읽기 때문에 외국인이 한국어를 읽는 것처럼 들린다. 정렬 품질도 같이 나빠진다. 그래서 기본을 MeloTTS로 두었다.

7지금 상태

서버는 완성됐다. UE 없이 전체 파이프라인이 검증됐다.

검증결과
단위 테스트 56개통과 (모델 없이 1초)
TTS 스모크melo·xtts 양쪽 통과
정렬 스모크통과
통합 왕복통과
LLM 죽었을 때error 프레임, 서버 생존

실측 속도 (RTX 2060 SUPER 8GB, MeloTTS GPU):

값
첫 프레임까지2577ms
3문장 턴 전체15.7초
VRAM 합계3.7GB / 8GB

첫 프레임 2.6초면 설계 목표(3초 이내 발화 시작)를 만족한다. TTS를 CPU로 내리면 턴 전체가 25초로 늘어난다.

CUDA 프로세스를 여러 개 띄우면 안 된다. 서버를 두 개 동시에 실행했더니 Ollama의 llama-server가 CUDA error: shared object initialization failed로 죽었다. VRAM 총량 문제가 아니라 컨텍스트 충돌이다.

UE 클라이언트는 시작 전이다. 얼굴 커브가 움직인다는 것만 확인했다 (CTRL_expressions_jawOpen).

8실행 방법

ollama serve
cd server && .venv/Scripts/python -m uvicorn app.main:app --port 8000

모델 로딩 완료 로그가 찍힌 뒤에 접속한다. UE 없이 확인하려면:

cd server && .venv/Scripts/python scripts/ws_client.py "오늘 뭐 했어?"

9다음 단계

UE 클라이언트 작업이다. 순서는 리스크가 큰 것부터다.

  1. 런타임 오디오 재생 — UE는 wav 바이트를 그대로 재생하지 못한다. USoundWaveProcedural로 직접 큐잉해야 한다. 여기서 막히면 나머지가 무의미하므로 가장 먼저 확인한다.
  2. WebSocket 연결 — Build.cs에 WebSockets, Json, JsonUtilities 추가. 프레임 파싱.
  3. viseme 재생 — 하드코딩한 배열로 먼저 입이 움직이는지 본다. CTRL_expressions_jawOpen 하나만으로 AA/NN/KK/sil 4종이 동작하므로, 나머지 커브 이름을 다 찾기 전에 시작할 수 있다.
  4. 전체 연결 — 서버 프레임을 큐에 쌓고 순차 재생.

그다음이 STT다. 마이크 입력을 텍스트로 바꿔 지금의 채팅 입력 자리에 넣으면 된다. 계약이 바뀌지 않으므로 서버는 user_message를 만드는 경로만 늘리면 된다.

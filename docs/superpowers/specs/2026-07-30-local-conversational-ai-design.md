# Local Conversational AI — 설계 문서

작성일: 2026-07-30

## 1. 개요

언리얼 엔진 5의 메타휴먼과 채팅으로 대화하는 프로그램. 사용자가 텍스트를 입력하면
로컬 LLM이 답변을 생성하고, 로컬 TTS가 음성을 만들며, 메타휴먼이 그 음성에 맞춰
입 모양을 움직인다. 답변 텍스트도 함께 화면에 표시한다.

성격: 취미 포트폴리오. 상업적 배포 계획 없음. 동시 사용자 1명 기준.

### 성공 기준

1. 사용자가 한국어 문장을 입력하면 3초 이내에 메타휴먼이 말을 시작한다.
2. 메타휴먼의 입 모양이 재생되는 음성의 모음과 시각적으로 일치한다.
3. TTS나 정렬 단계가 실패해도 대화가 끊기지 않고 자막은 계속 표시된다.

## 2. 확정 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 대화 언어 | 한국어 전용 | 범위 최소화 |
| 백엔드 | FastAPI 단일 프로세스 | AI 파이프라인이 파이썬. 언어 경계를 만들지 않음 |
| 통신 | WebSocket, 문장 단위 스트리밍 | 첫 발화까지의 지연 최소화 |
| LLM | Ollama + `gemma3n:e2b` | 8GB VRAM에서 XTTS와 공존 가능. vLLM은 VRAM 선점으로 부적합 |
| LLM 호출 방식 | `LLM_API`로 `ollama` / `openai` 선택 | 원격 llama.cpp는 OpenAI 호환이라 주소만 바꿔서는 안 됨 |
| TTS | XTTS-v2 (fp16) | 음성 복제 품질. 연구/데모 전용이므로 CPML 라이선스 무관 |
| 타임스탬프 | wav2vec2 CTC forced alignment (CPU) | MFA 대비 가볍고 빠름. 문장 스트리밍과 양립 |
| viseme 단위 | 음절 | 한국어 입 모양은 중성(모음)이 지배. 매핑 표가 짧아짐 |
| 대화 기억 | 세션 내 메모리 | 연결 = 세션. DB 불필요 |
| 클라이언트 | UE5, C++ 베이스 클래스를 블루프린트로 노출 | |
| 실행 위치 | UE 클라이언트와 서버는 별도 머신 | |

### 명시적으로 버린 선택지

- **gRPC** — UE에서의 protobuf 빌드 통합 비용이 WebSocket 대비 얻는 것보다 크다.
- **Node.js 게이트웨이** — 파이썬 파이프라인 앞에 다른 언어를 두면 프로세스 간
  경계가 늘어난다.
- **Spring Boot** — 위와 같은 이유. Java에서 XTTS·wav2vec2를 부를 방법이 없어
  파이썬 사이드카가 강제되는데, 그 오버헤드를 감수할 이유가 이 프로젝트에는 없다.
- **vLLM** — `gpu_memory_utilization` 기본값이 VRAM 90%를 선점해 XTTS와 공존하지 못한다.
- **Azure TTS** — 외부 API 의존은 "로컬" 전제를 깬다. 참고로 Azure는 viseme 이벤트를
  API가 직접 제공하므로, 채택했다면 정렬 단계 자체가 사라지는 다른 설계가 된다.
- **MFA (Montreal Forced Aligner)** — 문장당 1~3초가 걸려 문장 스트리밍의 이점을 없앤다.

## 3. 아키텍처

```
┌─ 1. Client (UE5) ─────────────────────────────────────┐
│  MetaHuman · ARKit 입술 커브 15종 · FInterpTo 보간      │
│  WebSocket Client / Audio Queue / Viseme Player       │
└────────▲─────────────────────────────│────────────────┘
         │ {text, audioB64, visemes[]} │ {"type":"user_message"}
         │  문장 단위 1프레임           ▼
┌────────┴──────────────────────────────────────────────┐
│  2+3. FastAPI 프로세스 (단일)                          │
│                                                       │
│  ┌ WS 핸들러 ────────────────────────────────────┐    │
│  │  세션 히스토리 (메모리, 연결 = 세션)            │    │
│  │  문장 경계 분할                                │    │
│  │  프레임 조립 · 실패 폴백                       │    │
│  └──┬───────────────────────────┬───────────────┘    │
│     │ httpx stream              │ 직접 함수 호출      │
│     ▼                           ▼                     │
│  (외부 프로세스)           [TTS → Align → Map]        │
│                            XTTS fp16   (GPU 2.5GB)    │
│                            wav2vec2    (CPU)          │
│                            viseme 매퍼 (순수 파이썬)   │
└───────────────────────────────────────────────────────┘
         │
         ▼
┌─ Ollama :11434 ── gemma3n:e2b (GPU 3GB) ──────────────┐
└───────────────────────────────────────────────────────┘
```

2층(프로토콜)과 3층(AI 파이프라인)은 **논리적으로는 분리하되 물리적으로는 한 프로세스**다.
파이썬끼리 HTTP를 태울 이유가 없다. 계층 의도는 파일 분리로 유지한다.

### 프로세스 구성 (서버 머신)

```
ollama serve          # 설치만, 작성할 코드 없음
uvicorn app.main:app  # 본 프로젝트 코드 전부
```

## 4. 컴포넌트

### 4.1 FastAPI 서버

파일 구조:

```
app/
  main.py         # FastAPI 앱, WebSocket 엔드포인트
  session.py      # 대화 히스토리, 문장 경계 분할
  llm.py          # Ollama 스트리밍 호출
  tts.py          # XTTS-v2 래퍼
  align.py        # wav2vec2 CTC forced alignment
  viseme.py       # 음절 → viseme 매핑
  config.py       # 모델 경로, 하이퍼파라미터
```

각 모듈의 책임:

| 모듈 | 하는 일 | 의존 |
|---|---|---|
| `main.py` | WS 연결 수락, 프레임 송수신, 예외를 error 프레임으로 변환 | `session` |
| `session.py` | 히스토리 보관, 토큰 스트림을 문장으로 분할, 파이프라인 순차 호출 | `llm`, `tts`, `align`, `viseme` |
| `llm.py` | `POST /api/chat`에 `stream=true`로 요청, 토큰을 async generator로 반환 | httpx |
| `tts.py` | 문장 → wav 바이트. 모델은 프로세스 시작 시 1회 로드 | TTS (idiap 포크) |
| `align.py` | (wav, 텍스트) → `[(음절, startMs, endMs)]`. 실패 시 예외 | torchaudio |
| `viseme.py` | 음절 리스트 → viseme 타임라인. 순수 함수, 외부 의존 없음 | 없음 |

`viseme.py`가 순수 함수인 점이 중요하다. 테스트가 가장 쉽고 튜닝이 가장 잦은 곳이다.

### 4.2 UE5 클라이언트

C++ 베이스 클래스를 만들고 블루프린트에서 상속·조립한다.

| 클래스 | 책임 |
|---|---|
| `UConversationClient` (Subsystem) | WebSocket 연결, 프레임 파싱, 재연결 |
| `USpeechQueue` | 수신 프레임을 큐잉, 앞 문장 재생이 끝나면 다음 문장 시작 |
| `UVisemePlayer` (AnimInstance 확장) | 재생 시각에 해당하는 viseme을 찾아 ARKit 커브에 반영 |

블루프린트에는 자막 UI, 카메라, 레벨 배치만 남긴다.

## 5. 통신 계약

이 계약이 설계의 고정점이다. TTS 엔진이나 정렬 방식을 바꿔도 이 스키마는 유지되며,
따라서 UE 코드는 수정되지 않는다.

### 5.1 클라이언트 → 서버

```json
{"type": "user_message", "text": "오늘 뭐 했어?"}
```

### 5.2 서버 → 클라이언트

문장 하나당 프레임 하나. 텍스트·오디오·viseme을 한 프레임에 담는다.

```json
{
  "type": "speech",
  "seq": 0,
  "text": "나는 하루 종일 여기 있었어.",
  "audioBase64": "UklGRi...",
  "visemes": [
    {"v": "AA", "start": 0,   "end": 140},
    {"v": "EU", "start": 140, "end": 260}
  ]
}
```

- `seq` — 0부터 증가. 클라이언트가 순서를 보장하는 데 쓴다.
- `audioBase64` — 16kHz 모노 WAV. 실패 시 `null`.
- `visemes` — `start`/`end`는 해당 문장 오디오 시작 기준 밀리초. 실패 시 `[]`.

턴 종료:

```json
{"type": "turn_end", "seq": 3}
```

오류:

```json
{"type": "error", "code": "LLM_UNAVAILABLE", "message": "Ollama 응답 없음"}
```

## 6. 파이프라인 상세

### 6.1 처리 흐름

```
1. 클라이언트가 user_message 전송
2. 히스토리에 append, system prompt와 함께 Ollama 호출 (stream=true)
3. 토큰을 버퍼에 모으다 문장 경계를 만나면 그 문장을 확정
4. 확정된 문장 → XTTS → wav
5. (wav, 문장) → wav2vec2 CTC → 음절별 [start, end]
6. 음절 → viseme 매핑
7. speech 프레임 조립하여 전송, seq 증가
8. 토큰 스트림이 끝날 때까지 3~7 반복
9. 잔여 버퍼가 있으면 마지막 문장으로 처리한 뒤 turn_end 전송
```

### 6.2 문장 경계 분할

`. ? ! …` 및 줄바꿈을 경계로 본다. 추가 규칙:

- 최소 길이 10자. 그보다 짧으면 다음 경계까지 합친다. `"응."` 같은 조각을 개별
  TTS로 돌리면 오디오가 부자연스럽게 끊긴다.
- 최대 길이 120자. 경계 없이 길어지면 강제로 자른다. LLM이 마침표를 안 찍는
  경우에 대비한다.

### 6.3 viseme 매핑

음절의 **중성(모음)이 그 음절의 기본 viseme을 결정한다.** 한국어 입 모양은 모음이 지배한다.
초성·종성은 기본 viseme을 대체하지 않고, 아래 "추가 규칙"에 따라 음절 구간의 일부만
덮어쓴다. 표의 자음 항목은 그 덮어쓰기에 쓰이는 viseme의 정의다.

#### 커브 이름 규칙

스파이크 A에서 확인한 결과, 메타휴먼 얼굴은 **ARKit 블렌드셰이프 이름을 직접 노출하지
않는다.** RigLogic 컨트롤 보드의 커브 이름을 쓰며 `CTRL_expressions_*` 형태다.

- 확인 완료: `CTRL_expressions_jawOpen` — 값 주입 시 턱이 벌어지는 것을 확인했다.
- 나머지 커브 이름은 미확인이다. 아래 표의 `jawOpen` 외 항목은 **가설**이며,
  구현 전에 에디터에서 실제 이름을 확인하고 갱신해야 한다.

실제 이름 확인 방법: Face 스켈레탈 메시의 Skeleton 에셋을 열고 Curves 패널에서 전체
커브 목록을 본다. 또는 Face AnimBP의 Modify Curve 노드 드롭다운에 나열된다.

| viseme | 트리거 | 주 커브 (`CTRL_expressions_` 접두사 생략) | 확인 |
|---|---|---|---|
| `AA` | ㅏ ㅑ ㅐ ㅒ | `jawOpen` 0.7 | ✅ |
| `EH` | ㅔ ㅖ ㅓ ㅕ | `jawOpen` 0.4 + 입꼬리 가로 확장 커브 0.3 | 부분 |
| `IH` | ㅣ | 입꼬리 당김 커브 0.5, `jawOpen` 0.15 | 부분 |
| `OH` | ㅗ ㅛ | 입술 깔때기 커브 0.6, `jawOpen` 0.4 | 부분 |
| `OU` | ㅜ ㅠ | 입술 오므림 커브 0.8 | 미확인 |
| `EU` | ㅡ ㅢ | 입꼬리 가로 확장 커브 0.4 | 미확인 |
| `PP` | 초성 ㅁ ㅂ ㅍ ㅃ | 입술 다뭄 커브 1.0 | 미확인 |
| `NN` | 초성 ㄴ ㄷ ㅌ ㄹ | `jawOpen` 0.2 | ✅ |
| `KK` | 초성 ㄱ ㅋ, 받침 ㅇ | `jawOpen` 0.25 | ✅ |
| `SS` | 초성 ㅅ ㅈ ㅊ | `jawOpen` 0.2 + 입꼬리 가로 확장 커브 0.2 | 부분 |
| `sil` | 무음 구간 | 전부 0 | ✅ |

메타휴먼 컨트롤 보드는 좌우 분리 커브(`...L` / `...R`)를 쓰는 경우가 많다. 발음용
입 모양은 좌우 대칭이므로 양쪽에 같은 값을 넣는다.

`jawOpen`만으로도 `AA`/`NN`/`KK`/`sil`이 동작하므로, **나머지 커브 이름을 확정하기 전에도
스파이크 B(하드코딩 viseme 재생)를 진행할 수 있다.** 턱 여닫힘만으로 입 움직임의 골격은
확인된다. 나머지 커브는 그 위에 얹는 개선이다.

추가 규칙:

- 초성이 ㅁ/ㅂ/ㅍ이면 음절 구간의 **앞 25%**를 `PP`로 덮는다. 입을 다물었다 여는
  동작이 시각적으로 가장 두드러진다.
- 종성이 ㅁ/ㅂ/ㅍ이면 음절 구간의 **뒤 20%**를 `PP`로 덮는다.
- 초성이 ㄴ/ㄷ/ㅌ/ㄹ, ㄱ/ㅋ, ㅅ/ㅈ/ㅊ이면 음절 구간의 **앞 15%**를 각각 `NN`, `KK`, `SS`로
  덮는다. 입 다뭄만큼 두드러지지 않으므로 구간을 짧게 잡는다.
- 초성 ㅇ은 무음이므로 덮어쓰지 않는다.
- 음절 사이 간격이 200ms를 넘으면 그 사이를 `sil`로 채운다.

예: `"밤"` (ㅂ + ㅏ + ㅁ), 구간 0~200ms → `PP` 0\~50, `AA` 50\~160, `PP` 160\~200.

UE 쪽에서는 목표 커브값으로 `FInterpTo`한다. 이산 전환을 그대로 적용하면 딱딱해 보인다.
보간 속도는 초기값 15로 두고 눈으로 보며 조정한다.

## 7. VRAM 예산 (8GB)

모두 실측치다 (RTX 2060 SUPER 8GB, MeloTTS 기준 구성).

| 상주 | 배치 | 사용량 |
|---|---|---|
| `gemma3n:e2b` (Ollama, Q4_K_M) | GPU | **1.6GB** |
| MeloTTS (기본 엔진) | GPU | **0.9GB** |
| XTTS-v2 (fp32, 대안 엔진) | GPU | 1.9GB |
| wav2vec2 CTC 한국어 | **CPU** | RAM ~1GB |
| 데스크톱 앱 (탐색기, 브라우저 등) | GPU | ~1.2GB |
| 합계 (MeloTTS 구성) | GPU | **3.7GB / 8GB** |

`gemma3n:e2b`의 디스크 크기는 5.6GB지만 실제 VRAM 점유는 1.6GB다. E2B는 레이어별
임베딩 중 일부만 상주시킨다. 디스크 크기로 예산을 잡으면 안 된다.

여유가 4GB 이상이므로 정렬기를 GPU로 올릴 수도 있다. 다만 CPU에서 문장당
100~200ms면 충분해 실익이 없다.

**주의 — CUDA 프로세스를 여러 개 띄우지 말 것.** 서버 인스턴스를 두 개 동시에
실행했더니 Ollama의 llama-server가 죽었다.

```
CUDA error: shared object initialization failed
llama-server process has terminated: exit status 0xc0000409
```

VRAM 총량이 부족해서가 아니다. 인스턴스 하나만 띄우면 같은 조합이 문제없이 돈다.

**fp16 로드는 포기했다.** `tts_model.half()`를 부르면 speaker encoder까지 fp16이 되는데
입력 파형은 fp32로 들어와 conv1d에서 죽는다. 실제 에러는 다음과 같다.

```
RuntimeError: Input type (torch.cuda.FloatTensor) and weight type
(torch.cuda.HalfTensor) should be the same
```

fp32로도 실측 1892MB에 그쳐(RTX 2060 SUPER 8GB 기준) 예산 안에 들어온다. 당초 우려했던
4.5GB는 과대 추정이었다.

wav2vec2를 GPU에 올릴 이유는 여전히 없다. CPU에서 문장당 100~200ms면 충분하다.

한국어 합성에는 `hangul_romanize` 패키지가 추가로 필요하다. 없으면
`Korean requires: hangul_romanize`로 실패한다.

## 8. 실패 처리

원칙: **어떤 실패에서도 대화는 계속된다. 텍스트가 최소 보장선이다.**

| 상황 | 동작 |
|---|---|
| Ollama 응답 없음 | `error` 프레임 전송. 클라이언트는 자막 영역에 오류 표시 |
| XTTS 실패 / OOM | `audioBase64: null`, `visemes: []`로 프레임 전송. 자막은 나가고 입은 움직이지 않음 |
| 정렬 실패 | 음절 균등 분배로 대체 (오디오 총 길이 ÷ 음절 수). 품질은 떨어지나 멈추지 않음 |
| WebSocket 끊김 | 클라이언트가 3회 재연결 시도. **재연결 시 대화 기록은 초기화된다** (연결 = 세션) |
| 히스토리 토큰 초과 | 오래된 턴부터 제거. system prompt는 항상 유지 |

정렬 실패 시의 균등 분배 폴백은 처음부터 구현한다. 이것이 있으면 wav2vec2 도입 전에도
파이프라인 전체를 돌려볼 수 있어 개발 순서가 유연해진다.

## 9. 테스트

| 대상 | 방법 | 판정 |
|---|---|---|
| `viseme.py` | 순수 함수 단위 테스트 | `"안녕하세요"` → viseme 5개 이상, 시간 구간이 겹치지 않고 단조 증가 |
| `session.py` 문장 분할 | 단위 테스트 | `"가나다라마바사. 아자차카타파하."` → 문장 2개. `"응."` → 다음 문장과 합쳐짐 |
| `align.py` | 통합 테스트 | 마지막 음절의 `end`가 wav 길이의 ±10% 이내 |
| 전체 파이프라인 | 파이썬 WebSocket 클라이언트 스크립트 | **UE 없이** 프레임 스키마·순서·폴백 검증 |
| UE 클라이언트 | 수동 확인 | 입 모양이 음성과 어긋나 보이지 않음 |

UE를 붙이기 전에 백엔드를 파이썬 스크립트만으로 완결시킨다. UE 빌드 사이클이 느려서
백엔드 버그를 UE에서 디버깅하면 시간이 몇 배로 든다.

## 11. 리스크와 미확인 항목

구현 착수 전 또는 초기에 확인이 필요한 항목이다.

| 항목 | 내용 | 대응 |
|---|---|---|
| XTTS-v2 한국어 품질 | 17개 지원 언어 중 한국어는 상대적으로 약하다. 실제 들어봐야 안다 | 초기에 짧은 문장으로 먼저 확인. 미달 시 MeloTTS-ko로 교체 |
| 참조 음성 확보 | XTTS는 음성 복제 방식이라 6초 이상의 깨끗한 참조 wav가 필요하다 | 준비 필요 |
| Coqui 프로젝트 상태 | 원 저장소는 2024년 아카이브됨 | 커뮤니티 포크 `idiap/coqui-ai-TTS` 사용 |
| 라이선스 | XTTS-v2는 CPML(비상업 전용) | 연구/데모 전용이므로 문제없음. 상업화 시 교체 필요 |
| `gemma3n:e2b` 한국어 품질 | 유효 2B급 모델의 한국어 응답 자연스러움은 미검증 | 미달 시 동급 VRAM 내에서 다른 모델 검토 |
| wav2vec2 한국어 모델 선정 | 어떤 체크포인트를 쓸지 미정 | 초기에 후보 1~2개 비교 |
| **UE 런타임 오디오 재생** | UE는 런타임에 wav 바이트를 재생하는 기능을 기본 제공하지 않는다. `USoundWaveProcedural`로 직접 큐잉해야 한다 | 초기에 별도로 검증. 여기서 막히면 일정 전체가 밀린다 |
| ~~메타휴먼 커브 구동 방식~~ | **해소됨 (2026-07-30).** `CTRL_expressions_jawOpen` 주입으로 턱이 움직이는 것을 확인 | 나머지 커브 이름만 추가 확인 필요 (6.3절 참조) |

커브 구동이 확인되면서 UE 쪽 최대 불확실성은 사라졌다. 남은 UE 리스크는 런타임 오디오
재생 하나다. 백엔드는 경로가 명확하므로, 다음 순서로 진행한다.

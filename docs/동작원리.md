# Local Conversational AI — 동작 원리

메타휴먼과 한국어로 대화하는 프로그램이다. 사용자가 **말하거나** 텍스트를 입력하면
로컬 LLM이 답하고, 로컬 TTS가 음성을 만들고, 메타휴먼이 그 음성에 맞춰 입을 움직인다.

외부 API를 쓰지 않는다. 전부 한 대의 PC에서 돈다.

---

## 1. 전체 그림

```
┌─ 클라이언트 (UE5) ────────────────────────────────────┐
│  메타휴먼 · ARKit 입술 커브 · 자막 UI                  │
│  마이크 녹음 / WebSocket / 오디오 큐 / viseme 재생기   │
└──▲────────▲─────────────────│──────────────│──────────┘
   │        │                 │              │ {"type":"audio_message",
   │        │ {text,          │ {"type":     │  "audioBase64":"UklGRi..."}
   │        │  audioBase64,   │  "user_      │
   │ {"type":│  visemes[]}    │  message",   │
   │  "transcript",           │  "text":...} │
   │  "text":"오늘 뭐 했어?"}  ▼              ▼
┌──┴────────┴───────────────────────────────────────────┐
│  서버 (FastAPI, 파이썬 단일 프로세스)                  │
│                                                       │
│  ┌ WebSocket 핸들러 ────────────────────────────┐     │
│  │  audio_message -> STT -> transcript (무상태)  │     │
│  │  user_message  -> 아래 턴 파이프라인          │     │
│  │  세션 히스토리 (메모리, 연결 = 세션)          │     │
│  │  문장 경계 분할  <- 스트리밍의 심장            │     │
│  │  프레임 조립 · 실패 폴백                      │     │
│  └──┬───────────────┬───────────┬──────────────┘     │
│     │ HTTP 스트림   │ 직접 호출 │ 직접 호출          │
│     ▼               ▼           ▼                     │
│  (외부 프로세스)  STT       TTS -> 정렬 -> viseme     │
│                   faster-    MeloTTS   (GPU 0.9GB)    │
│                   whisper    wav2vec2  (CPU)          │
│                   (GPU 0.9GB) 매퍼     (순수 파이썬)   │
└───────────────────────────────────────────────────────┘
         │
         ▼
┌─ (원격) llama.cpp :8080 ── EXAONE-3.5-7.8B ───────────┐
└───────────────────────────────────────────────────────┘
```

LLM은 2026-08-06부터 다른 PC의 llama.cpp를 쓴다. OpenAI 호환 API라 `LLM_API=openai`로
붙는다. 그래서 이 머신에서 띄울 프로세스는 하나뿐이다.

```
uvicorn app.main:app  # 이 프로젝트의 서버 코드 전부
```

UE는 서버 하나만 안다. LLM도 TTS도 UE에 노출되지 않는다.

## 2. 한 번의 대화가 흐르는 순서

사용자가 "오늘 뭐 했어?"라고 말하거나 입력했을 때 벌어지는 일이다.

### 0단계 — (음성일 때) 말이 글자가 된다

마이크를 쓰면 그 앞에 한 단계가 붙는다. UE가 녹음한 WAV를 보내고 서버가 받아적어
돌려준다. **이건 턴이 아니다** — 받아적기만 하고 LLM은 건드리지 않는다.

```json
-> {"type": "audio_message", "audioBase64": "UklGRi..."}
<- {"type": "transcript", "text": "오늘 뭐 했어?"}
```

받아적은 글자는 입력란에 들어간다. 잘못 알아들은 문장이 그대로 LLM에 가는 것보다
사용자가 한 번 보는 편이 낫다. 자세한 건 7장에 있다.

### 1단계 — 질문이 서버로

UE가 WebSocket으로 보낸다. 음성이든 타이핑이든 여기서부터는 똑같다.

```json
{"type": "user_message", "text": "오늘 뭐 했어?"}
```

### 2단계 — 히스토리에 쌓고 LLM 호출

서버는 이 연결의 대화 기록에 질문을 붙이고, system 프롬프트와 함께 LLM에
스트리밍 요청을 보낸다.

```python
[
  {"role": "system",    "content": "너는 사용자와 편하게 대화하는 친구다..."},
  {"role": "user",      "content": "오늘 뭐 했어?"}
]
```

LLM은 두 종류를 붙일 수 있다. `LLM_API` 환경변수로 고른다.

| | `ollama` (기본) | `openai` |
|---|---|---|
| 대상 | 로컬 Ollama | 원격 llama.cpp, vLLM |
| 경로 | `/api/chat` | `/v1/chat/completions` |
| 응답 형식 | 줄 단위 JSON | SSE (`data: {...}`) |
| 토큰 위치 | `message.content` | `choices[0].delta.content` |

주소만 바꿔서는 안 된다. 경로도 응답 형식도 다르기 때문이다. 나머지 코드는
`stream_chat()` 하나만 부르므로 이 차이는 `llm.py` 안에서 끝난다.

현재는 `openai`를 쓴다. `run.bat`가 `LLM_API`와 `LLM_BASE_URL`을 설정한다.

### 3단계 — 토큰을 모으다 문장이 완성되면 자른다

LLM은 글자를 조금씩 흘려보낸다. 서버는 이걸 버퍼에 모으다가 문장이 끝나면
그 문장만 떼어낸다.

```
"음," -> "음, 그냥" -> "음, 그냥 책 읽으면서" -> "음, 그냥 책 읽으면서 커피 마셨어!"
                                                                          ↑ 여기서 확정
```

**이게 체감 속도의 핵심이다.** 전체 답변을 다 기다리면 5~8초 침묵이 생긴다.
첫 문장만 나오면 바로 말을 시작하므로 2초 안에 입이 움직인다.

자르는 규칙은 네 가지다.

- 경계 문자는 `. ? ! … 줄바꿈`
- 10자 미만이면 다음 경계까지 합친다. `"응."`을 따로 합성하면 오디오가 뚝 끊긴다
- 120자를 넘으면 강제로 자른다. LLM이 마침표를 안 찍는 경우 대비
- 읽을 내용이 없으면 버린다. LLM이 이모지만 따로 뱉는 일이 잦은데, 그대로
  합성하면 입은 가만있고 소리만 1초 난다

### 4단계 — 문장을 음성으로

확정된 문장 하나를 TTS에 넣는다.

```
"음, 그냥 책 읽으면서 커피 마셨어!"  ->  44100Hz 파형 3916ms
```

### 5단계 — 음성과 글자를 시간 축에서 맞춘다 (강제 정렬)

만들어진 음성과 원래 문장을 wav2vec2 CTC 모델에 같이 넣으면, **각 음절이
몇 밀리초에 발음되는지** 나온다.

```
안      0 ~   340ms
녕    340 ~   440ms
하    440 ~   681ms
세    681 ~   801ms
요    801 ~  1883ms
```

이 단계가 없으면 입 모양을 언제 바꿔야 할지 알 수 없다.

### 6단계 — 음절을 입 모양으로

한국어 입 모양은 **중성(모음)이 지배한다.** `밤`을 발음할 때 입을 크게 벌리는 건
`ㅏ` 때문이지 `ㅂ`이나 `ㅁ` 때문이 아니다.

그래서 음절마다 중성으로 기본 입 모양을 정하고, 초성·종성은 앞뒤 일부만 덮어쓴다.

```
"밤" (ㅂ + ㅏ + ㅁ), 구간 0~200ms

  PP   0 ~  50ms   앞 25%  — 초성 ㅂ, 입을 다물었다 연다
  AA  50 ~ 160ms   가운데  — 중성 ㅏ, 턱을 벌린다
  PP 160 ~ 200ms   뒤 20%  — 종성 ㅁ, 다시 다문다
```

입 모양은 10종이다.

| viseme | 언제 | 입 모양 |
|---|---|---|
| `AA` | ㅏ ㅑ ㅐ ㅘ | 턱을 크게 벌림 |
| `EH` | ㅓ ㅕ ㅔ ㅝ | 중간으로 벌림 |
| `IH` | ㅣ | 옆으로 당김 |
| `OH` | ㅗ ㅛ | 둥글게 |
| `OU` | ㅜ ㅠ ㅚ ㅟ | 오므림 |
| `EU` | ㅡ ㅢ | 옆으로 폄 |
| `PP` | ㅁ ㅂ ㅍ | 완전히 다뭄 |
| `NN` | ㄴ ㄷ ㅌ ㄹ | 살짝 벌림 |
| `KK` | ㄱ ㅋ | 살짝 벌림 |
| `SS` | ㅅ ㅈ ㅊ | 좁게 |
| `sil` | 무음 | 닫음 |

### 7단계 — 프레임 하나로 묶어 전송

텍스트·오디오·입 모양을 한 덩어리로 보낸다.

```json
{
  "type": "speech",
  "seq": 0,
  "text": "음, 그냥 책 읽으면서 커피 마셨어!",
  "audioBase64": "UklGRi...",
  "visemes": [
    {"v": "EU", "start": 0,   "end": 340},
    {"v": "NN", "start": 340, "end": 440}
  ]
}
```

3~7단계가 문장마다 반복된다. 답변이 끝나면 마지막에 알린다.

```json
{"type": "turn_end", "seq": 2}
```

### 8단계 — UE가 재생

프레임을 큐에 쌓고, 앞 문장 재생이 끝나면 다음 문장을 시작한다. 재생 시각에
해당하는 viseme을 찾아 메타휴먼 얼굴 커브에 값을 넣는다.

값을 그대로 넣으면 입이 딱딱 끊기므로 `FInterpTo`로 부드럽게 잇는다.

## 3. 왜 이렇게 만들었나

### 왜 파이썬 한 프로세스인가

TTS(MeloTTS, XTTS)와 정렬기(wav2vec2)는 파이썬 라이브러리다. 자바에서 부를
방법이 사실상 없다. 그래서 파이썬 프로세스는 어차피 떠야 한다.

처음에는 Spring Boot를 앞에 두는 안을 검토했다. 그러면 프로세스가 하나 늘고
서비스 간 HTTP 홉이 생긴다. 취미 프로젝트에서 그 비용을 치를 이유가 없어
FastAPI 단일로 정했다.

계층은 문서상 나눠두되 물리적으로는 한 프로세스다. 파이썬끼리 HTTP를 태울
이유가 없다.

### 왜 WebSocket인가

문장이 완성될 때마다 서버가 먼저 밀어야 한다. REST면 클라이언트가 계속
물어봐야 하고, 그러면 문장 단위 스트리밍의 이점이 사라진다.

### 왜 음절 단위인가

음소 단위로 하면 매핑 표가 커지고 정렬도 어려워진다. 한국어는 입 모양이
모음에 지배되므로 음절 단위로도 화면에서 차이가 거의 없다.

### 왜 정렬기를 CPU에 두나

GPU 8GB를 TTS(0.9GB)와 STT(0.9GB)가 쓰고, 같은 화면에 메타휴먼도 올라간다.
정렬기는 문장당 100~200ms면 충분해서 GPU에 올릴 이유가 없다.
(LLM 1.6GB는 원격으로 옮긴 뒤로 이 카드에서 빠졌다.)

### 왜 받아적기는 턴을 돌리지 않나

말한 걸 바로 LLM에 넣으면 잘못 알아들은 문장이 그대로 질문이 된다. 받아적기만
돌려주고 보낼지는 사용자가 정한다.

덕분에 서버의 STT 경로가 완전히 무상태가 된다. 연결마다 오디오 버퍼를 들고 있을
필요가 없고, 실시간 갱신은 클라이언트가 전체를 다시 보내는 것으로 해결된다.

## 4. 고장 나도 대화는 계속된다

**텍스트가 최소 보장선이다.** 무슨 일이 생겨도 자막은 나간다.

| 고장 | 결과 |
|---|---|
| LLM이 죽음 | `{"type":"error","code":"LLM_UNAVAILABLE"}`. 서버는 안 죽는다 |
| TTS 실패 | `audioBase64: null`, `visemes: []`. 자막만 나가고 입은 가만있다 |
| 정렬 실패 | 오디오 길이를 음절 수로 균등 분배. 정확도는 떨어지지만 멈추지 않는다 |
| STT 실패 | `{"type":"error","code":"STT_FAILED"}`. 대화는 그대로 살아 있고 타이핑으로 계속할 수 있다 |
| 아무 말도 못 알아들음 | `{"type":"transcript","text":""}`. 빈 문자열도 답이다 — 이게 와야 클라이언트가 녹음 상태를 푼다 |
| 연결 끊김 | UE가 지수 백오프(1→5초 상한)로 계속 재연결. 음성 모드는 풀리고 재생 큐는 즉시 비운다. **대화 기록은 초기화된다** (연결 = 세션) |
| 히스토리 초과 | 오래된 대화부터 버린다. system 프롬프트는 항상 유지 |

백오프 상한이 5초인 건 서버 기동에 2분이 걸리기 때문이다. 그동안 PIE를 켜두면
간격이 상한까지 벌어져, 서버가 살아난 뒤에도 그만큼 더 기다리게 된다. 상대는
로컬호스트라 자주 두드려도 비싸지 않다.

## 5. 코드 구조

```
server/app/
  main.py       FastAPI 앱, WebSocket 엔드포인트, 모델 사전 로딩
  session.py    대화 히스토리, 턴 오케스트레이션
  llm.py        LLM 스트리밍 호출 (Ollama / OpenAI 호환)
  stt.py        faster-whisper 래퍼. WAV -> 문장
  sentence.py   토큰 스트림을 문장으로 분할
  pipeline.py   speech 프레임 조립, 실패 폴백
  tts.py        TTS 프로토콜, MeloTTS·XTTS 구현체, WAV 인코딩
  align.py      균등 분배 폴백, wav2vec2 CTC 정렬
  viseme.py     음절 -> viseme 매핑
  hangul.py     한글 자모 분해
  config.py     환경변수 설정
```

의존 방향은 한 방향이다.

```
main -> session -> pipeline -> tts, align, viseme -> hangul
     -> stt
```

`stt`는 턴 파이프라인에 끼지 않는다. `main`이 직접 부르고 결과를 그대로 돌려준다.
받아적기는 대화 상태를 만들지 않기 때문이다.

`hangul`, `viseme`, `sentence`는 **아무것도 import하지 않는 순수 함수 모듈**이다.
그래서 모델도 GPU도 없이 테스트할 수 있다. 전체 단위 테스트 70개가 2초 안에 끝난다.

클라이언트도 같이 적어둔다.

```
UE5_Client/Source/UE5_Client/
  ConversationClient   WebSocket 소유, 프레임 파싱, 재연결
  MicRecorder          마이크 캡처, WAV 조립, 무음 감지
  SpeechQueue          문장 오디오를 순서대로 재생, 재생 위치 제공
  VisemeDriver         재생 위치 -> 메타휴먼 얼굴 커브값
  ConversationWidget   UI 상태 기계 (대화 모드, 마이크 개폐, 전송 시점)
```

넷 다 `UGameInstanceSubsystem`이거나 컴포넌트다. 위젯이 사라져도 대화 세션은 살아 있다.

## 6. TTS 엔진 두 가지

`TTS_ENGINE` 환경변수로 고른다. 기본은 `melo`.

| | MeloTTS | XTTS-v2 |
|---|---|---|
| 한글 처리 | 직접 | 로마자로 바꾼 뒤 다국어 모델이 읽음 |
| 발음 | 자연스러움 | 외국인 억양 |
| 음성 복제 | 불가 | 가능 (참조 음성 6초) |
| 같은 문장 길이 | 4357ms | 8534ms |
| VRAM | 902MB | 1899MB |
| 라이선스 | MIT | CPML (비상업 전용) |

XTTS는 음성 복제가 되지만 한국어를 로마자로 바꿔 읽기 때문에 외국인이 한국어를
읽는 것처럼 들린다. 정렬 품질도 같이 나빠진다. 그래서 기본을 MeloTTS로 두었다.

## 7. 음성 입력

### 왜 faster-whisper인가

CTranslate2 런타임이라 `transformers`와 무관하다. MeloTTS가 `transformers==4.27.4`를
못박아 `--no-deps`로 설치돼 있는데, transformers 기반 whisper를 얹으면 그 핀 충돌에
같이 묶인다.

모델은 `large-v3-turbo`, `int8_float16`으로 돌린다. `float16`이 0.3초쯤 빠르지만
VRAM이 0.9GB에서 1.6GB로 는다. 8GB 카드에 MeloTTS·wav2vec2·메타휴먼이 같이 올라가
있어 정확도 차이가 거의 없는 쪽을 골랐다.

두 가지 옵션이 중요하다.

- `vad_filter=True` — 무음 구간에서 whisper는 학습 데이터의 자막 상투구를 지어낸다
  ("시청해주셔서 감사합니다"). Silero VAD가 무음을 먼저 잘라내 이걸 막는다
- `condition_on_previous_text=False` — 켜두면 앞 문장을 조건으로 삼아 짧은 발화에서
  같은 말을 반복하는 루프에 빠진다

### 말하는 중에 글자가 실시간으로 찍히는 원리

whisper 인코더는 입력을 무조건 30초로 패딩한다. **그래서 인식 비용이 길이와 거의
무관하다.**

| 녹음 길이 | 인식 시간 |
|---|---|
| 4.3초 | 0.38초 |
| 8.7초 | 0.39초 |
| 17.4초 | 0.44초 |

이 성질 덕분에 조각을 이어 붙이는 스트리밍 구조가 필요 없다. 1초마다 **지금까지
녹음된 전체**를 다시 보내 통째로 다시 받아적으면 된다. 클라이언트가 버퍼를 들고
있으므로 서버는 완전히 무상태다.

대신 두 가지 한계가 따라온다.

- 글자 단위가 아니라 1초 단위로 갱신된다
- 문장이 길어지면 앞부분 해석이 바뀔 수 있다. "사과" -> "사과가 아니라"

앞 요청의 답이 오기 전에는 다음 것을 보내지 않는다. 인식이 느려지면 갱신 간격이
알아서 벌어진다.

**전송량이 이 구조의 천장이다.** 48kHz 모노 16비트면 초당 96KB씩 늘고 매번 처음부터
다시 보낸다. 그래서 한 발화가 60초(`MaxRecordSeconds`)를 넘으면 거기서 끊는다.

### 대화 모드 두 가지

시작할 때 고르고, 대화 중에도 바꿀 수 있다. 마이크를 열고 실시간으로 받아적는
부분은 둘이 같다. **다른 건 언제 보내느냐뿐이다.**

| | 실시간 대화 | 푸시 투 토크 |
|---|---|---|
| 마이크 열기 | 모드를 고르는 즉시 | 마이크 버튼을 누를 때 |
| 무음 2초 | 자동 전송 | 무시, 계속 녹음 |
| 마이크 버튼 재누름 | 취소 (녹음 버림) | 말 끝냄 -> 받아적어 입력란에 |
| 전송 | 자동 | 사용자가 엔터/보내기 |

실시간은 대화가 자연스럽지만 잘못 인식된 문장이 그대로 나간다. 푸시 투 토크는
느리지만 고칠 수 있다.

### 자기 목소리에 자기가 대답하는 걸 막는 법

AI가 말하는 동안 마이크를 닫는다. 스피커 소리가 그대로 들어오면 방금 자기가 한 말을
질문으로 받아 무한 루프가 된다. 헤드폰을 써도 이 편이 안전하다.

닫혀 있는 동안 버튼이 회색이 되고 입력란에 "마이크 꺼짐" 안내가 뜬다. 상태 표시는
한 줄로 모았다.

| 상태 | 표시 |
|---|---|
| 마이크 열림 | `● 녹음 중` |
| 닫혔고 받아적기 대기 | `텍스트로 변환 중...` |
| AI가 말하는 중 | `AI 말하는 중 — 마이크 꺼짐` |
| 그 외 | 현재 모드 이름 |

두 모드가 같은 표시를 쓴다. 실시간 모드도 말이 끝나면 마이크를 닫고 받아적기를
기다리므로 그동안 `텍스트로 변환 중...`이 뜬다.

### 말이 끝났는지 어떻게 아나

소리 크기(RMS)만 본다. 라이브러리를 붙일 만한 일이 아니고, 마이크 버튼으로 이미 한 번
걸러진 뒤다. `conv.SpeechLevel`(기본 0.005)을 넘으면 말, 그 아래로 `conv.SilenceMs`
(기본 2000ms)만큼 이어지면 끝으로 본다.

마이크 감도와 방 소음에 따라 달라진다. PIE 콘솔에서 `conv.MicDebug 1`을 켜면 0.5초마다
실제 RMS가 로그에 찍힌다. 말할 때와 조용할 때 값을 보고 그 사이에서 고른다.

기본값 0.005는 실측으로 정했다. WASAPI 48kHz 마이크에서 조용할 때 0.0006, 말할 때
0.5초 최대가 0.008~0.012였다. 처음 잡았던 0.02는 목소리보다 높아서 말이 통째로
무음으로 잡혔고, `bHeardSpeech`가 서지 않아 무음 카운트가 시작조차 안 됐다.
자동 전송이 안 걸린 게 아니라 걸릴 수가 없었다.

무음 길이 2초는 짧게 잡으면 문장 중간 숨 쉬는 데서 끊기기 때문이다. 끊고 나서 다시
말을 이으면 그 뒷말이 다음 턴으로 밀린다.

### 마지막 받아적기를 기다린다

말이 끝난 시점에 중간 결과가 아직 서버에 가 있을 수 있다. 그 답이 먼저 도착하는데,
그건 말을 하다 만 문장이다. 그대로 보내면 잘린 문장이 LLM으로 간다.

`PendingAudio`가 0이 될 때까지 기다린다. 한 연결 안에서 메시지가 순서대로 처리되므로
0이 되는 순간의 받아적기가 마지막 녹음의 것이다.

### 받아적은 뒤 바로 보낸다

받아적기가 도착하면 그 프레임에 전송한다. 입력란에 넣은 글자는 같은 프레임에 지워져
화면에 뜬 적이 없게 되지만, 전송이 대화창에 말풍선을 남기므로 사용자는 그걸로
뭐라고 인식됐는지 확인한다.

처음에는 `SendDelay`(0.7초)만큼 입력란에 띄워두고 읽을 시간을 줬다. 뺐다. 말이
끝나면 곧바로 나가는 게 실시간 모드의 뜻이고, 그 시간이 그대로 발화 사이 공백으로
쌓였다. 인식된 문장을 고치고 싶으면 푸시 투 토크를 쓴다.

### 클라이언트 쪽 선택

- **리샘플링을 안 한다.** 48000 -> 16000이 정확히 3배라 단순 솎아내기가 되지만 그러면
  에일리어싱이 심하다. 제대로 하려면 저역 통과가 필요한데, faster-whisper가 PyAV로
  이미 올바르게 리샘플한다. 장치 레이트 그대로 보낸다
- **`Audio::FAudioCapture`를 쓴다.** `UAudioCaptureComponent`는 마이크 입력을 *재생*하는
  물건이지 PCM을 꺼내는 물건이 아니다
- **`Build.cs`에 `AudioCapture`를 넣어야 한다.** `AudioCaptureCore`만 넣으면 컴파일은
  되지만 런타임에 장치를 못 찾는다. 실제 구현(`AudioCaptureWasapi`)을 등록하는 건
  플러그인 모듈 쪽이다

## 8. 지금 상태

**서버는 완성됐다.** UE 없이 전체 파이프라인이 검증됐다.

| 검증 | 결과 |
|---|---|
| 단위 테스트 70개 | 통과 (모델 없이 2초) |
| TTS 스모크 | melo·xtts 양쪽 통과 |
| 정렬 스모크 | 통과 |
| STT 스모크 | 통과 (TTS 출력을 다시 받아적는 왕복) |
| 통합 왕복 | 통과 |
| LLM 죽었을 때 | error 프레임, 서버 생존 |

실측 속도 (RTX 2060 SUPER 8GB, MeloTTS GPU):

| | 값 |
|---|---|
| 첫 프레임까지 | 2577ms |
| 3문장 턴 전체 | 15.7초 |
| STT 모델 로딩 | 27초 (기동 시 1회) |
| STT 인식 (예열 후) | 0.39초 |
| VRAM 합계 | 4.6GB / 8GB |

첫 프레임 2.6초면 설계 목표(3초 이내 발화 시작)를 만족한다. TTS를 CPU로 내리면
턴 전체가 25초로 늘어난다.

**GPU 경합에 주의한다.** 같은 STT 측정이 에디터를 켠 채로는 2.3초, 끄면 0.39초가
나왔다. 6배 차이다. 실사용 값은 그 사이 어딘가다.

**CUDA 프로세스를 여러 개 띄우면 안 된다.** 서버를 두 개 동시에 실행했더니
Ollama의 llama-server가 `CUDA error: shared object initialization failed`로 죽었다.
VRAM 총량 문제가 아니라 컨텍스트 충돌이다. (LLM을 원격으로 옮긴 뒤로는 해당 없다.)

**UE 클라이언트는 대화가 도는 상태다.** 입력 → 응답 → 오디오 재생 → 말풍선 표시까지
확인했다 (2026-08-06). 그 뒤로 viseme 재생(`VisemeDriver`)과 음성 입력이 붙었고
**컴파일까지는 검증됐지만 PIE 실사용 확인은 아직이다.** 자세한 내용은
`docs/superpowers/specs/`의 설계 문서를 본다.

## 9. 실행 방법

```bash
server/run.bat
```

`LLM_API=openai`와 원격 llama.cpp 주소를 잡아준다. 직접 띄우려면:

```bash
cd server && .venv/Scripts/python -m uvicorn app.main:app --port 8000
```

`모델 로딩 완료` 로그가 찍힌 뒤에 접속한다. 모델 세 개를 올리므로 2분쯤 걸린다.
코드를 고친 뒤 다시 띄울 때는:

```bash
server/restart.bat
```

8000 포트를 잡고 있는 서버를 죽이고 다시 띄운다. `uvicorn --reload`는 못 쓴다 —
파일이 바뀔 때마다 모델을 처음부터 다시 올린다.

UE 없이 확인하려면:

```bash
cd server && .venv/Scripts/python scripts/ws_client.py "오늘 뭐 했어?"
```

받아적기만 따로 보려면 (녹음 파일 없이 TTS 출력을 되먹인다):

```bash
cd server && .venv/Scripts/python scripts/smoke_stt.py
```

## 10. 다음 단계

서버는 완성됐고 클라이언트는 통신·오디오·UI·음성 입력이 다 붙었다. 남은 것은
검증과 튜닝이다.

1. **PIE 실사용 확인** — viseme 재생과 두 대화 모드가 아직 화면에서 확인되지 않았다.
   컴파일만 통과한 상태다.
2. **무음 감지 실사용 확인** — 임계값을 실측으로 0.005까지 내렸고 무음 길이는 2초로
   잡았다. PIE에서 실제로 자동 전송이 걸리는지, 문장 중간에 끊기지는 않는지 봐야 한다.
3. **첫 발화 지연** — 목표는 3초인데 실측 6.7초다. 어느 단계가 먹는지 계측이 없다.

알고 있지만 아직 안 고친 것 둘.

- `align.py`가 어휘에 없는 음절(팁, 늑, 콕 등)을 만나면 예외를 던지고 균등 분배로
  떨어진다. 입 모양이 소리보다 밀린다
- LLM이 JSON이나 백틱을 뱉으면 MeloTTS가 `KeyError`로 죽는다. 자막만 나가고
  소리가 없다
